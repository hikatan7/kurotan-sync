ユーザーが複数ファイル(PDF/PPT/Word等)を指定して「統合して最終版を作って」と依頼したら、以下の定型フローで実施する(2026-07-22に病院経営デッキで確立)。

**手順:**
1. **全ソース読込**: テキスト層のないPDFはpypdfium2で画像化(scale≒1.4)してRead。内容サマリーをscratchpadのmdに保存(コンテキスト要約対策+進捗管理を兼ねる)
2. **構成設計**: 重複を特定して統合、おすすめ枚数(章立て)を表で提案。深堀り(資料間の数値接続・解釈追加)と参考文献(一次データ+公的文献)を必ず追加
3. **段階作成**: ユーザー承認を得ながら作成(まず1枚→承認→続き、が既定パターン)。文字密度は高め(1枚あたり多め)が好み
4. **品質確認**: PPTはpython-pptx生成→PowerPoint COMでPNGエクスポート→目視QA(はみ出し・重なり修正)。WordはWord COM。[[env-word-com-doc-generation]]
5. **元ファイル整理(2026-07-26にユーザー指示で改定)**: 完成後、引用済み元ファイルに**両方**を適用する。**完全削除はしない。**
   - **(a) 先頭に `統合済_` を付けてリネーム** — 例: `診療報酬解説_最終版.pdf` → `統合済_診療報酬解説_最終版.pdf`
   - **(b) 同フォルダ内サブフォルダ「_統合済み元資料」へ移動** — 移動はSHA256ハッシュ照合付き。OneDrive同期下のため[[env-onedrive-desktop-file-ops]]の作法に従う

   ユーザーの指示は「名前の先頭に統合済と入れる、**または**統合済フォルダにまとめる」だったが、既定は両方適用とする。**Why:** フォルダだけだと後で元ファイルが別の場所に移動された瞬間に統合元だと分からなくなる。実際2026-07-26に「統合元がどれか分からない」となり全ドライブを走査する羽目になった。名前に入れておけばファイル単体でも判別でき、`統合済_` でGrep/検索すれば全ドライブから一発で回収できる。
6. **記録を必ず残す**: 統合のたびに「成果物のフルパス＋元ファイルのフルパス一覧」をプロジェクトメモリに書く。**ファイル名でなくフルパスで**。2026-07-26に「統合元がどれか分からないので消したい」と聞かれた際、記録が説明的ラベル(例:「静岡vs清水会計構造」)だけだったため実ファイルを特定できなかった。

**統合元を削除してよいかの判定法(2026-07-26確立):** 成果物と元ファイルの本文を抽出し、漢字4字以上の語集合の含有率を測る。
- **含有率99%以上＝コピー的統合** → 削除して情報損失ほぼゼロ(例: ファイナンステキストの詳細版8件は99.1〜100%)
- **含有率25〜70%＝凝縮リライト** → 元ファイル固有の情報が残る。削除は要確認(例: 手術室経営の統合詳説2026は25〜68%)
- **テキスト層ゼロのPDF(NotebookLM系)は含有率が測れない** → 統合版に文字として反映されていない可能性が高く、最も慎重に扱う
成果物に出典スライド/参考文献があれば、それが元資料を特定する一次情報になる。

**Why:** ユーザーは複数AIで同テーマの資料を多数作るため重複が溜まる。集約+情報補完+PC整理を一括で行いたい。
**How to apply:** 「統合して」「まとめて最終版を」等の依頼で即このフローを適用。デザイン規約は[[project-hospital-mgmt-deck]]参照(紺16324F基調・カードF2F6FA・Key Insightバー・Yu Gothic UI・出典フッター・頁番号)。
